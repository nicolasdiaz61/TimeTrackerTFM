# Diseño: multi-compania

Fecha: 2026-10-20 · Fase: sdd-design · Modo: openspec · Base: `proposal.md`, `exploration.md` (fuente), `AGENTS.md`, ADR 0011, 0013, 0017, 0018 y 0019, `openspec/specs/` y el código vigente de `src/` citado en cada decisión. Rama: `docs/multi-compania-propuesta`.

Convención: **DD-n** = decisión de diseño; **V-n** = verificación que apply (o una persona) hace antes de dar un paso por bueno (sección 9); **Q-n** = pregunta abierta residual (sección 10); **TC-n** = caso de prueba imprescindible del diseño (sección 6; no confundir con el alias `T-x` de comandos de `tasks.md`). Lo que no se comprobó en esta fase se marca **«no verificado»**. Los identificadores van en inglés; los nombres de variables de entorno y de rutas los fijan las specs (`specs/**`) y las decisiones del usuario.

Regla de precedencia (alineación del 2026-10-20): mandan las specs de `specs/**` y las decisiones confirmadas del usuario; este diseño se corrige para coincidir con ellas. El «Registro de alineación» (sección 11) resume lo histórico y lo vigente.

Estado del código leído: `UserAccount` (inmutable, `Create` con `managerId`), `UserConfiguration` (`ux_users_email`, `fk_users_users_manager_id`, `ix_users_manager_id`), `TimeEntryConfiguration` (sin FK a `users`, `xmin`, `ux_time_entries_employee_id_open`), `AssistantSettingsConfiguration` (PK `id`, `ck_assistant_settings_singleton`, `xmin`), `AssistantSettingsAuditConfiguration` (`ix_assistant_settings_audit_occurred_at`), migración `AddAssistantAuditImmutability` (función `assistant_settings_audit_append_only` y dos triggers), `UserRepository`, `TimeEntryRepository`, `DemoTimeEntryStore`, `AssistantSettingsStore`, `AssistantSettingsLoader`, `AssistantSettingsPoller`, `InMemoryAssistantQuota`, `AesGcmCredentialProtector` (AAD `tt-assistant-credential|v1|{provider}|{version}`), `AuthenticationServiceCollectionExtensions.RejectInvalidClaims`, `JwtAccessTokenIssuer`, `HttpContextCurrentUser`, `AuthEndpoints`, `RateLimitingServiceCollectionExtensions`, `DemoUsersSeeder`. Versiones fijadas en `Directory.Packages.props`: EF Core 10.0.12 y Npgsql EF 10.0.3.

Hallazgo que corrige a la exploración: `ForwardedHeaders` **no está activo por defecto**; el ADR 0013 lo define opcional (`ForwardedHeaders__Enabled`, apagado por defecto, `ForwardedHeaders__Hops`). Que esté activo en producción es una comprobación pendiente (V-7), no un hecho: un validador de arranque lo exige (con `Hops` efectivo >= 1) cuando el registro está abierto en producción (DD-19).

**Hecho verificado el 2026-10-20 (despliegue en Railway):** los servicios `api` y `web` de Railway **no tienen repositorio de GitHub conectado** (`source.repo = null`). No hay autodespliegue: solo se despliega con `railway up` manual, de modo que **fusionar una PR no despliega nada**. Salvedad: si algún día se conecta el autodespliegue desde `main`, **hay que rehacer el plan de despliegue por fases** (DD-4, DD-24 y tarea 9), porque fusionar pasaría a desplegar y las PR 1 y 1b no podrían fusionarse seguidas. Esto contrasta con `AGENTS.md` §7 («el despliegue es automático desde la rama principal»), que describe una intención no cumplida hoy en Railway (riesgo anotado en la sección 8; la actualización de `AGENTS.md` va en la PR 8). Sigue **sin verificar** el valor real de `Database__ApplyMigrationsOnStartup` en producción (V-6): cada despliegue manual tiene una puerta previa que lo comprueba.

## 1. Enfoque técnico

Una base de datos compartida; cada fila de negocio lleva `company_id`. El aislamiento es híbrido y cada capa cubre el fallo de la anterior:

1. **Esquema (verdad estructural):** claves foráneas compuestas `(company_id, …)` hacia `users(company_id, id)`; ninguna fila puede apuntar a un usuario de otra compañía aunque el código falle.
2. **Código (filtro global que falla cerrado):** `HasQueryFilter` aplicado por convención a todo tipo de entidad con `company_id` (la tabla `companies` no lleva filtro: es la propia tabla de compañías), alimentado por `ICompanyContext`; sin compañía no hay filas. Las escrituras pasan por una guarda en `SaveChanges`. Las rutas que necesitan saltarse el filtro son una lista cerrada, vigilada por pruebas de arquitectura.
3. **Pruebas:** dos compañías A y B con la misma forma de datos recorren todos los endpoints, las herramientas del asistente y las restricciones.

La compañía sale solo del claim `cid` del JWT (el nombre visible viaja en `cname`, solo para presentación). La configuración del asistente y su runtime pasan de singleton a «una por compañía». La migración es expandir/contraer. El registro público queda tras `Registration__Enabled` (apagada), un código de invitación y un límite por IP.

```
Cliente ──JWT(sub, role, cid, cname, [mcp])──> Api
  UseAuthentication ─ RejectInvalidClaims (sub, role, cid válidos)
  CompanyContextMiddleware (Api) ──> ICompanyContext (adaptador en Api, ámbito, escritura única) <── cid
  PasswordChangePendingMiddleware ──> 403 salvo endpoints marcados (mcp)
  UseAuthorization ─ RateLimiter ─ endpoint ─ caso de uso (ICurrentUser.CompanyId)
                                                  │
                                    Repositorios (DbContext con filtro global)
                                                  │
        TimeTrackerDbContext ── filtro: company_id = CurrentCompanyId (Guid.Empty si no hay) ── guarda de escritura
                                                  │
        PostgreSQL: FK compuestas, PK company_id, triggers de auditoría intactos

Rutas fuera del HTTP autenticado (lista cerrada, DD-9):
  login (correo) · versiones del poller · registro · siembra · cargador por compañía
        └─ IgnoreQueryFilters (2 sitios) o ICompanyScopeFactory.CreateScope(companyId)
```

## 2. Decisiones de diseño

### DD-1. Una BD compartida con `company_id`; capas y dónde vive cada pieza

| Capa | Cambios | Notas |
|---|---|---|
| Domain | `Company` (id, nombre, `NormalizeName`, estado, `UsesPlatformAssistant`, `CreatedAt`); constante `Company.DefaultId`; `CompanyId` en `UserAccount` y `TimeEntry` (explícito); `UserAccount.Create(id, companyId, email, displayName, passwordHash, role, managerId, mustChangePassword)`, `UserAccount.MustChangePassword`, `ChangePassword(hash)` (cambia el hash y deja `MustChangePassword` en falso) y `RegenerateTemporaryPassword(hash)` (cambia el hash y mantiene `MustChangePassword` en verdadero); `TimeEntry.Start(companyId, employeeId, type, at)` (la compañía de `Pause`/reanudación se hereda del intervalo que se cierra) | Reglas de nombre y normalización con cobertura 100 % (AGENTS §5). Sin EF ni ASP.NET. |
| Application | `ICurrentUser.CompanyId`, `ICompanyContext` (puerto, sin dependencias externas), `PasswordPolicy`, `RegisterCompanyUseCase`, `CreateTeamMemberUseCase`, `ResetTemporaryPasswordUseCase`, `ChangePasswordUseCase`, puertos `ICompanyRegistrationStore`, `ICompanyRepository`, `ITemporaryPasswordGenerator`, `IInviteCodeValidator`; `IAssistantQuota` y `IAssistantRuntimeReloader` reciben `companyId`; `IAssistantCredentialProtector` recibe `companyId` | Cobertura >= 80 %. | Api | adaptador `AmbientCompanyContext` de `ICompanyContext` (y del setter) y `CompanyContextMiddleware` (que no fija compañía en las rutas marcadas `SkipCompanyContext`, hoy solo `register-company`), middleware de cambio de contraseña pendiente, claims, endpoints nuevos, políticas de tasa, validadores de opciones, siembra | Composition root. |

### DD-2. Modelo de datos

Nombres en `snake_case`, como el esquema actual.

**`companies`** (tabla nueva)

| Columna | Tipo | Restricción |
|---|---|---|
| `id` | uuid | PK; `Guid.CreateVersion7` salvo la compañía por defecto (DD-3) |
| `name` | varchar(100) | NOT NULL, `CHECK char_length(btrim(name)) BETWEEN 1 AND 100` (spec `company-isolation` y `company-registration`: 1 a 100 caracteres) |
| `name_normalized` | varchar(100) | NOT NULL, índice único `ux_companies_name_normalized` |
| `status` | varchar(16) | NOT NULL DEFAULT `'Active'`, `CHECK status IN ('Active','Suspended')` |
| `uses_platform_assistant` | boolean | NOT NULL DEFAULT `false` (DD-13). Sexta columna, recogida en la spec `company-isolation` (decisión del usuario; Q-3 resuelta) |
| `created_at` | timestamptz | NOT NULL |

`name_normalized` = recorte, espacios internos colapsados a uno y `ToLowerInvariant` (cultura invariante), **sin plegar acentos** (spec), calculado solo en `Company.NormalizeName` (una regla, como `UserAccount.NormalizeEmail`). Solo se impide el duplicado exacto normalizado (sin normalización Unicode `FormKC`, decisión del usuario; Q-14 resuelta). `status` no se cambia desde la interfaz (fuera de alcance); un operador lo cambia por SQL y el login lo respeta (DD-6).

**`users`**

| Cambio | Detalle |
|---|---|
| `company_id uuid` | NOT NULL tras la migración B; FK `fk_users_companies_company_id` a `companies(id)` |
| `must_change_password boolean` | NOT NULL DEFAULT `false` (se añade en A) |
| Clave alternativa `(company_id, id)` | Restricción UNIQUE `ux_users_company_id_id` (EF `HasAlternateKey`: es la forma de declarar el destino de una FK compuesta; en PostgreSQL equivale al índice único pedido) |
| FK compuesta `fk_users_users_company_id_manager_id` | `(company_id, manager_id)` -> `users(company_id, id)`, `NO ACTION`, **MATCH SIMPLE** (valor por defecto de PostgreSQL: con `manager_id` nulo no se comprueba nada). Sustituye a `fk_users_users_manager_id` |
| Índice | `ix_users_manager_id` se sustituye por `ix_users_company_id_manager_id` (consulta de reportes directos) |
| Se conservan | `ux_users_email` único global (una persona, una compañía), `ck_users_*` |
| Concurrencia | `xmin` como token de concurrencia de `UserAccount` (columna de sistema, sin columna nueva): lo usan `ChangePassword` y la regeneración de la contraseña temporal (DD-21); un conflicto se traduce en `409` |

**`time_entries`**

| Cambio | Detalle |
|---|---|
| `company_id uuid` | NOT NULL tras B |
| FK compuesta `fk_time_entries_users_company_id_employee_id` | `(company_id, employee_id)` -> `users(company_id, id)`, `NO ACTION`. Cierra el hueco del ADR 0011 (disparador: llega el alta de usuarios). Antes de B se comprueban los huérfanos (DD-4, V-1) |
| Se conservan | `xmin`, `ux_time_entries_employee_id_open`, `ix_time_entries_employee_id_clock_in_at` (el filtro por compañía es un predicado extra sobre esos índices; sin índice nuevo) |

**`assistant_settings`**: PK `company_id` (uuid, FK a `companies(id)`); se eliminan `id` y `ck_assistant_settings_singleton`; se conservan todas las demás columnas y CHECK y **`xmin`** como token de concurrencia. El nombre de la PK vigente se lee de la migración `AddAssistantSettings` al escribir la migración B.

**`assistant_settings_audit`**: `company_id uuid NOT NULL` con FK a `companies(id)`; el índice `ix_assistant_settings_audit_occurred_at` se sustituye por `ix_assistant_settings_audit_company_id_occurred_at (company_id, occurred_at DESC)`. Los triggers de solo inserción no se tocan (DD-5). Sin FK de `actor_id` (igual que hoy: la auditoría no depende del ciclo de vida del usuario).

**Tabla de tokens:** no hay. La «contraseña temporal de un solo uso» es una contraseña normal con `must_change_password = true`: se sustituye por la que elige la persona y la marca vuelve a `false` (DD-21). No se guarda ningún secreto temporal aparte del hash. La baja de usuarios sigue fuera de alcance: la FK es `NO ACTION` y un borrado falla con `23503`, de modo que la futura «baja» deberá decidir entre baja lógica y borrado en cascada (se anota en el ADR 0020).

### DD-3. Compañía por defecto de id fijo y compañía de plataforma

La migración A crea una compañía de id fijo `Company.DefaultId = 00000000-0000-7000-8000-000000000001`, nombre ASCII `Demo` y `name_normalized = 'demo'` (ASCII para que `lower()` de SQL y `NormalizeName` de C# coincidan sin depender del idioma de la base de datos; una prueba compara el literal de la migración con la constante). La spec fija solo que existe una compañía por defecto de id constante, `Active`, que es también la compañía demo. Todo dato existente pasa a ella. Es la «compañía demo» **y** la única con `uses_platform_assistant = true` (A lo fija a `true` para conservar el comportamiento actual: la clave `Ai__ApiKey` sigue sirviendo a los datos existentes). El registro público crea siempre `uses_platform_assistant = false`; ningún endpoint lo modifica.

| Opción para «la clave de plataforma solo para la demo» | Ventaja | Inconveniente | Decisión |
|---|---|---|---|
| Columna `uses_platform_assistant` | Explícita y auditable por SQL; permite que el product owner active otra compañía sin código | Una columna más | **Elegida** |
| Comparar con `Company.DefaultId` en código | Sin columna | Acopla el comportamiento a una constante; no sirve si producción tiene datos reales en la compañía por defecto | Descartada |
| Variable `Ai__PlatformCompanyId` | Sin esquema | Un identificador más en el entorno; se desincroniza de la base de datos | Descartada |

Si producción contiene usuarios que no son de demostración (V-1), la compañía por defecto los aloja igualmente; el nombre y la bandera se corrigen por SQL antes de abrir el registro (Q-1).

### DD-4. Migración expandir/contraer (A y B)

Dos migraciones escritas a mano (SQL) sobre el modelo destino. El `Designer` y el snapshot de A reflejan el modelo final (las propiedades `CompanyId` son `Guid` no nulo): EF solo compara el snapshot con el modelo, no con la base de datos, y así `dotnet ef migrations has-pending-model-changes` queda vacío tras B (V-5).

**Migración A, `AddCompanies` (expandir; segura para el código anterior)**

1. `CREATE TABLE companies` y `INSERT` de la compañía por defecto (`uses_platform_assistant = true`).
2. `users`: `ADD COLUMN company_id uuid NULL`, `ADD COLUMN must_change_password boolean NOT NULL DEFAULT false`; `UPDATE users SET company_id = '<DefaultId>'`.
3. `time_entries`: `ADD COLUMN company_id uuid NULL`; `UPDATE` a la compañía por defecto (también los huérfanos: la comprobación es de B).
4. `assistant_settings`: `ADD COLUMN company_id uuid NULL`; `UPDATE` de la fila singleton.
5. `assistant_settings_audit`: `ADD COLUMN company_id uuid NOT NULL DEFAULT '<DefaultId>'`, **sin `UPDATE`** (DD-5).
6. Sin FKs ni PK nuevas: el código anterior, que no conoce `company_id`, sigue funcionando (las filas que escriba en la ventana quedan con `NULL` y la auditoría recibe el valor por defecto).

**Migración B, `EnforceCompanyIsolation` (contraer)**, en este orden, cada migración en su transacción (el DDL de PostgreSQL es transaccional):

1. Relleno residual de las filas escritas por código anterior: `UPDATE ... SET company_id = '<DefaultId>' WHERE company_id IS NULL` en `users`, `time_entries` y `assistant_settings`.
2. **Comprobación de huérfanos que aborta con un mensaje claro:** `DO $$ ... RAISE EXCEPTION 'time_entries huérfanos: %', n` si hay fichajes cuyo `employee_id` no existe en `users`. B nunca borra ni inventa usuarios. Qué hacer con los huérfanos lo decide una persona antes (exportar y borrar, o reasignar a un usuario real; V-1). El ADR 0011 anticipaba justo este coste.
3. `SET NOT NULL` en las tres columnas y `ALTER COLUMN company_id DROP DEFAULT` en la auditoría (ya no puede haber escritores antiguos).
4. `users`: UNIQUE `(company_id, id)`; FK a `companies`; se elimina `fk_users_users_manager_id`; FK compuesta del responsable; intercambio de índice.
5. `time_entries`: FK compuesta del empleado.
6. `assistant_settings`: se elimina el CHECK del singleton, se sustituye la PK por `company_id`, se elimina la columna `id`, FK a `companies`.
7. Auditoría: FK a `companies` e índice `(company_id, occurred_at DESC)`.

**Reversibilidad y `Down`**

| Migración | `Down` | Condición y pérdida |
|---|---|---|
| B | Elimina FKs compuestas, UNIQUE y FKs a `companies`, devuelve las columnas a NULL, restaura `id smallint DEFAULT 1` con PK y `ck_assistant_settings_singleton`, repone índices antiguos | **Aborta con `RAISE EXCEPTION` si `count(*)` de `companies` es mayor que 1, o si `users` contiene más de un `company_id` distinto** (mensaje claro con el número de compañías, sin datos personales; no modifica nada). La condición **no** depende del número de filas de `assistant_settings`: con dos compañías y una sola fila de configuración el `Down` perdería igualmente la separación. Con varias compañías ya creadas no hay `Down`: revertir solo antes de abrir el registro |
| A | Elimina las columnas `company_id` y `must_change_password` y la tabla `companies` | Pierde el vínculo de compañía y la marca de contraseña temporal |

El `Down` de A no viola el trigger de auditoría: `ALTER TABLE ... DROP COLUMN` no dispara triggers por fila. Una prueba de migración con datos (sección 6, TC-18) ejecuta `Up A`, `Up B`, `Down B`, `Down A` y comprueba que los triggers siguen presentes (`pg_trigger`) y que un `UPDATE`/`DELETE`/`TRUNCATE` sobre la auditoría sigue fallando.

**Orden de despliegue de las migraciones (separación real de A y B).** Con `Database__ApplyMigrationsOnStartup=true` todas las migraciones pendientes se aplican en el mismo arranque, así que A y B en una misma publicación no se separarían. Se publican en despliegues distintos: A en PR 1; B en una PR 1b posterior (DD-24), cuando el código de PR 1 ya escribe `company_id` en todo `INSERT`. Así, si Railway solapa la instancia nueva y la antigua durante unos segundos (V-6), el código antiguo nunca choca con un `NOT NULL`. Como hoy **fusionar no despliega** (hecho verificado del encabezado), la separación se garantiza en el despliegue manual: la PR 1 y la PR 1b **nunca se despliegan seguidas ni juntas**, con una ventana de observación entre ambas (tarea 9). Si se conectara el autodespliegue, este plan debe rehacerse.

**Copia de seguridad, ensayo y ejecución en producción** (procedimiento; nada de esto está verificado en Railway):

1. Antes de cada despliegue con migración: copia lógica (`pg_dump -Fc`) y comprobación de que se restaura en un PostgreSQL local (misma versión mayor que la de Railway; V-4). La copia gestionada de Railway depende del plan y no se da por hecha (V-3).
2. Ensayo en dos partes (V-11): **parte 1, antes de desplegar la PR 1**: restaurar la copia en un contenedor local, `Up A`, `Down A` y arrancar la API contra el resultado de `Up A` con la suite mínima; **parte 2, antes de desplegar la PR 1b**: `Up A`, comprobación de huérfanos (debe abortar B), `Up B`, `Down B` (con una compañía funciona; con dos aborta), `Down A` y arranque de la API. Si no hay copia utilizable, ensayo con la base sembrada por `DemoUsersSeeder`/`DemoDataSeeder` más filas de auditoría y un fichaje huérfano creado a propósito.
3. Consultas previas (V-1): usuarios que no son de demostración, `time_entries` huérfanos, filas de `assistant_settings` y recuento de auditoría.
4. Cómo aplicar. **Todo script manual con `psql` se ejecuta con `-v ON_ERROR_STOP=1` y `--single-transaction`** (un error no deja cambios parciales ni sigue ejecutando el resto):

| Vía | Cuándo | Estado |
|---|---|---|
| `Database__ApplyMigrationsOnStartup=true` al desplegar | Migración A (aditiva, tras copia y ensayo), solo si V-6 confirma ese valor el mismo día del despliegue | Mecanismo existente (`DatabaseMigrationHostedService`); valor actual en producción **no verificado** |
| Script `dotnet ef migrations script --idempotent` aplicado con `psql -v ON_ERROR_STOP=1 --single-transaction` mediante `railway connect` (o proxy TCP público temporal) | Migración A si V-6 indica `false`, migración B, cualquier `Down` y cualquier caso con huérfanos | **No verificado** (acceso desde fuera y versión de `psql`; V-3, comprobada antes de desplegar la PR 1) |
| `railway run dotnet ef database update` desde un equipo local | Alternativa | **No verificado**: `railway run` inyecta las variables del servicio, pero `${{Postgres.PGHOST}}` apunta a la red privada (`*.railway.internal`), que no se resuelve fuera de Railway; haría falta el proxy TCP público (mayor superficie) |

   Antes de B se pone `Database__ApplyMigrationsOnStartup=false` (cambiar una variable de Railway redespliega el servicio con el código ya desplegado) para que ningún despliegue aplique B sin el control manual. Como las PR 2 a 8 no llevan migraciones, la variable puede quedarse en `false` tras B.

**Puertas de cada despliegue manual (`railway up`).** Ningún despliegue empieza sin: (a) V-6 comprobada **ese día** (valor de `Database__ApplyMigrationsOnStartup` leído de Railway y anotado); (b) copia `pg_dump -Fc` hecha y restaurada en local, si el despliegue lleva migración; (c) el healthcheck de Railway configurado sobre `/health` y observado antes y después; (d) rollback de código preparado (identificada la versión anterior desplegable), válido solo mientras el esquema siga siendo compatible con ella; (e) aprobación explícita del responsable. Para la PR 1b además: `ApplyMigrationsOnStartup=false` ya aplicado, V-1 resuelta, V-11 parte 2 anotada, ventana de observación de la PR 1 cumplida y una breve ventana de mantenimiento (sin tráfico de escritura) para aplicar B por la vía de V-3 y desplegar enseguida el código de la 1b, que adapta el almacén de la configuración del asistente a la clave primaria `company_id` (puente transitorio, DD-14).

**Procedimiento de rollback de producción (un rollback de código NO revierte el esquema):**

1. `Registration__Enabled=false` (si estaba abierta). Con más de una compañía real, **no** ejecutar `Down`: el `Down` de B aborta (hay más de una compañía); se restaura la copia o se corrige hacia delante.
2. Dejar de servir tráfico de escritura (escalar la API a 0 o retirar el despliegue).
3. Copia nueva.
4. Ejecutar `Down B` y luego `Down A` (hasta `AddAssistantAuditImmutability`) por la vía de script (`ON_ERROR_STOP=1`, `--single-transaction`).
5. Solo entonces redesplegar el código antiguo, con `Database__ApplyMigrationsOnStartup=false`.
6. Comprobar `/health`, login y un fichaje.

**Tras abrir el registro no hay `Down`** (hay varias compañías): el plan es la **corrección hacia delante (fix-forward)**: cerrar el registro (`Registration__Enabled=false`), corregir el defecto en código nuevo y desplegarlo con `railway up` o, como último recurso, restaurar la copia aceptando la pérdida de los datos posteriores. Revertir la PR 4b tras abrir el registro no es una opción (DD-14).

**Advertencia:** el rollback de un solo clic de Railway devuelve el binario antiguo contra el esquema nuevo (los `INSERT` de `time_entries` fallan por `company_id NOT NULL`, el almacén antiguo lee `assistant_settings.id`). Se documenta en el runbook y en el ADR 0020 (que entra en la PR 4a, DD-24): no usarlo con B aplicada sin `Down` previo. Hasta que el ADR exista, las descripciones de las PR 1, 1b, 2 y 3 llevan esta advertencia de rollback («un rollback de código no revierte el esquema»).

### DD-5. Auditoría: relleno de `company_id` sin `UPDATE`

El trigger `trg_assistant_settings_audit_no_update_delete` rechaza todo `UPDATE` de fila, así que un `UPDATE ... SET company_id` fallaría. Solución: `ADD COLUMN company_id uuid NOT NULL DEFAULT '<DefaultId>'` (PostgreSQL 11 o superior almacena el valor como metadato sin reescribir la tabla ni ejecutar `UPDATE`; la versión del servidor de Railway **no está verificada**, V-4) y quitar el `DEFAULT` en B. No se tocan la función ni los triggers (ni `DISABLE TRIGGER`, que exigiría privilegio de propietario y dejaría una ventana). Mientras el `DEFAULT` existe, el código anterior sigue insertando auditoría sin conocer la compañía y esas filas reciben la compañía por defecto, que es la única existente en ese momento.

### DD-6. Identidad: claim `cid`, `ICurrentUser.CompanyId` y `RejectInvalidClaims`

- `JwtAccessTokenIssuer` añade `cid = user.CompanyId` (constante `JwtDefaults.CompanyClaim = "cid"`), `cname = nombre de la compañía` (`JwtDefaults.CompanyNameClaim = "cname"`) y, solo con `must_change_password`, `mcp = "true"` (`JwtDefaults.PasswordChangePendingClaim`, DD-21). Así lo exige la spec `authentication` y lo confirma el usuario: el nombre viaja en el token **para que `me` no consulte la base de datos**. `cname` es solo de presentación: no interviene en ninguna decisión de autorización y no figura en ningún otro claim ni respuesta distinta de login, registro, cambio de contraseña y `me`.
- `ICurrentUser` gana `Guid CompanyId`; `HttpContextCurrentUser` lo lee del claim ya validado (sin consultar la base de datos) y **lanza una excepción** si el principal no está autenticado o el claim falta, no es un GUID o es `Guid.Empty` (spec `authentication`; no hay compañía por defecto).
- `RejectInvalidClaims` exige además `cid` GUID distinto de `Guid.Empty` (y, si existe `mcp`, que valga `"true"`). Un token sin `cid`, con `cid` no GUID o vacío falla con 401 (falla cerrado). **Efecto del despliegue:** todos los tokens vigentes caducan como máximo a los 30 minutos y las personas vuelven a iniciar sesión; la Web ya trata el 401 como sesión caducada.
- Login: tras verificar la contraseña y antes de emitir el token, si la compañía no está `Active` se responde el mismo 401 genérico (interruptor de operador por SQL; el tiempo de verificación de contraseña se mantiene constante porque el hash se verifica siempre antes, DD-6 de `LoginUseCase`). La compañía (nombre y estado) se lee por clave primaria con `ICompanyRepository.FindLoginInfoAsync`; como `companies` no lleva filtro (DD-8), esa lectura **no** usa `IgnoreQueryFilters`. **La misma comprobación de estado `Active` se aplica a toda operación que emite un token nuevo:** `POST /api/auth/change-password` (compañía `Suspended` → el mismo `401` genérico, sin emitir token ni cambiar el hash) y el registro (la compañía recién creada es `Active`; el token se emite por el mismo camino). La emisión de tokens pasa por un único colaborador de Application que lee `FindLoginInfoAsync` y comprueba el estado, de modo que ninguna ruta de renovación de sesión se salte la regla.
- `LoginResult`/`UserSummary` incorporan `CompanyName` y `MustChangePassword`; las respuestas de login, registro y cambio de contraseña los incluyen en `user`. **`GET /api/auth/me` los toma solo de los claims `cname` y `mcp`, sin consultar la base de datos** (la prueba arranca con una cadena de conexión inexistente). Límite aceptado: el nombre mostrado puede estar obsoleto hasta 30 minutos (en este cambio la compañía no puede renombrarse).
- Nunca se expone `companyId` en ninguna respuesta ni petición (prueba sobre `openapi.json`, DD-9); `companyName` aparece solo en las respuestas de login, registro, cambio de contraseña y `me`.
- **Límites aceptados y documentados** (ADR 0020): con token de 30 minutos, una compañía suspendida o un rol cambiado conservan acceso hasta que caduque el token; no hay revocación (fuera de alcance).

### DD-7. `ICompanyContext`, ámbito HTTP y guarda de escritura

`ICompanyContext { Guid? CompanyId { get; } }` es un puerto de `Application/Identity` sin dependencias externas. Su adaptador `AmbientCompanyContext` vive **solo en `TimeTracker.Api`** (`Api/Security`, ámbito `Scoped`; spec `solution-architecture`: puerto en Application, adaptador solo en Api, Infrastructure sin `HttpContext`) y es de **escritura única**:

- `ICompanyContextSetter.Set(Guid)` (interfaz declarada en Infrastructure; no es un puerto de Application) asigna la compañía una sola vez; un segundo `Set` con otro valor lanza `InvalidOperationException`. `AmbientCompanyContext` implementa `ICompanyContext` y `ICompanyContextSetter`.
- En HTTP, `CompanyContextMiddleware` (Api; tras `UseAuthentication`, antes de `UseAuthorization`) toma la compañía de `ICurrentUser.CompanyId` (el claim `cid` ya validado) y llama a `Set`. Una petición anónima o con token inválido deja el contexto vacío y el middleware no lee `ICurrentUser`. **Excepción:** en los endpoints marcados con los metadatos `SkipCompanyContext` (solo `POST /api/auth/register-company`) el middleware no fija nada aunque la petición lleve un token vigente: el registro ignora el token y crea la compañía en su propio ámbito (DD-19), de modo que no hay `500` ni fuga entre la compañía del token y la nueva. Una prueba de arquitectura comprueba que solo ese endpoint lleva el marcador.
- Fuera de HTTP, `ICompanyScopeFactory.CreateScope(companyId)` (interfaz en Infrastructure; `CompanyScopeFactory` en Infrastructure depende solo de las interfaces) crea un `IServiceScope` nuevo y hace `Set` mediante el setter registrado en la raíz de composición (Api); lo usan el cargador y el poller del asistente (puente transitorio y después el registro de instantáneas), la siembra, el almacén de registro de compañías, el validador de arranque de usuarios demo y las pruebas de integración. Hay una sola vía para «actuar como una compañía».
- **Excepción acotada a «sin localizadores de servicios» (AGENTS §3).** `ICompanyScopeFactory.CreateScope` y el contexto ambiental (`AmbientCompanyContext`) funcionan como un localizador de servicios restringido: crean un ámbito y resuelven en él dependencias. Se acepta porque el poller, la siembra y el registro necesitan actuar fuera del HTTP autenticado y no hay otra forma de dar a un `DbContext` una compañía distinta de la de la petición. La excepción se limita con una **lista cerrada de llamadores en `src/`** (`AssistantSettingsLoader` y `AssistantSettingsPoller` mientras exista el puente, `AssistantRuntimeRegistry`, `CompanyRegistrationStore`, `DemoUsersSeeder`, `DemoDataSeeder` y el validador de arranque de usuarios demo), vigilada por una prueba de arquitectura (cada llamador nuevo exige tocar la prueba y revisar la decisión), y se registra en el ADR 0020 (PR 4a). Las pruebas de integración la usan libremente (la prueba analiza solo `src/`).
- **Regla de dependencias (AGENTS §3):** Api -> Infrastructure -> Application -> Domain. `AmbientCompanyContext` (Api) implementa una interfaz de Infrastructure y un puerto de Application: ambas flechas son legales (la Api es el composition root y ya referencia las dos capas). No hay conflicto con AGENTS.md; lo vigilan `DependencyRuleTests`, que también exigen que Infrastructure no referencie `HttpContext` (V-15).
- **Sin compañía en el contexto (decisión del usuario; Q-11 resuelta):** `ICompanyContext` expone `Guid? CompanyId` (nulo = sin compañía, fallo cerrado en lectura: cero filas, sin error) y solo `ICurrentUser.CompanyId` lanza una excepción (spec `authentication`); no se devuelve nunca una compañía por defecto.

`TimeTrackerDbContext` recibe `ICompanyContext` y expone `Guid CurrentCompanyId => companyContext.CompanyId ?? Guid.Empty`. `Guid.Empty` no coincide con ninguna fila (la FK a `companies` lo impide): **sin compañía no se devuelve nada**. `DesignTimeDbContextFactory` y las pruebas usan un contexto vacío o fijo.

**Guarda de escritura:** el `DbContext` sobrescribe `SaveChanges`/`SaveChangesAsync`; para cada entrada `Added`, `Modified` o `Deleted` de un tipo con `CompanyId` exige `CompanyId == CurrentCompanyId` y que nadie modifique la propiedad `CompanyId`; si no, lanza `CompanyScopeViolationException` (un 500 genérico y un registro sin datos; spec: se rechaza sin escribir nada). Cierra el hueco de `Update(entidadDesconectada)`, que evita el filtro de lectura. `Company` no tiene `CompanyId` y queda fuera de la guarda; solo la crean el registro y la siembra. El registro de compañía **no** hace `Set` en Application (eso rompería AGENTS §3: Application no conoce el contexto ni el setter): `CompanyRegistrationStore` (Infrastructure) abre `CreateScope(nuevoId)` y escribe compañía y Manager con el `DbContext` de ese ámbito, cuyo contexto ya es la compañía nueva; así los usuarios de la compañía nueva pasan la guarda y **no existe ninguna ruta de escritura exenta**. El caso de uso de Application solo llama al puerto `ICompanyRegistrationStore.CreateAsync`.

| Opción | Decisión |
|---|---|
| Holder de escritura única en Api alimentado por middleware | **Elegida**: Infrastructure no depende de ASP.NET; un único punto de verdad; cumple la spec (adaptador solo en Api) |
| `ICompanyContext` que lee `IHttpContextAccessor` | Descartada: no sirve fuera de HTTP (poller, siembra) |
| Pasar `companyId` a cada método de repositorio | Descartada: un parámetro olvidado es justo la fuga que se quiere evitar; el filtro lo hace por convención |

### DD-8. Filtro global que falla cerrado, por convención

Un único bucle en `OnModelCreating`, después de `ApplyConfigurationsFromAssembly`, recorre `modelBuilder.Model.GetEntityTypes()` y a cada tipo con propiedad `CompanyId` (`users`, `time_entries`, `assistant_settings`, `assistant_settings_audit`) le aplica `HasQueryFilter(e => EF.Property<Guid>(e, "CompanyId") == CurrentCompanyId)` (expresión construida con una referencia al contexto, como el patrón documentado de multiinquilino). **`Company` no lleva filtro** (spec `company-isolation`: «La tabla `companies` NO lleva filtro»); contiene solo nombre y estado, y su lectura la encapsulan `CompanyRepository` y el almacén de registro (propuesta de vigilancia: prueba de arquitectura que limite el uso de `DbSet<Company>` a esos tipos y a la siembra). Ninguna configuración por entidad aplica el filtro a mano, así que una entidad nueva con `CompanyId` lo hereda. Una prueba de modelo (sección 6, TC-5) falla si algún tipo del modelo con `company_id` no tiene filtro; la lista de excepciones arranca **vacía**.

Puntos a probar (V-2, V-9): que el filtro construido por reflexión se parametriza por la instancia del contexto actual (dos contextos con compañías distintas no se contaminan); que `ExecuteUpdate`/`ExecuteDelete` respetan el filtro (la prueba de arquitectura los prohíbe en `src/` igualmente, DD-9); que `Find`/`FindAsync` **no** lo aplican (se prohíben).

### DD-9. Rutas explícitas permitidas y vigilancia por pruebas de arquitectura

**Lista cerrada de `IgnoreQueryFilters` (2 sitios en `src/`):**

| # | Sitio | Motivo | Lo que devuelve |
|---|---|---|---|
| 1 | `UserRepository.FindByEmailAsync` | El login no tiene compañía: el correo es único global | `UserAccount` (con `CompanyId`) |
| 2 | `AssistantSettingsStore.ListVersionsAsync` | El poller global lee `(company_id, xmin)` de todas las compañías | Solo identificador y versión; sin entidades con seguimiento |

La spec `company-isolation` fija exactamente estos dos sitios (`UserRepository.FindByEmailAsync` y `AssistantSettingsStore.ListVersionsAsync`) y exige que la lista no contenga entradas sin uso. `CompanyRepository.FindLoginInfoAsync(companyId)` (nombre y estado de la compañía del usuario recién autenticado) **ya no es un sitio de la lista**: `companies` no lleva filtro (DD-8), así que es una lectura por PK normal. Tampoco necesitan saltarse el filtro: las pruebas de unicidad del registro (se apoyan en las restricciones `ux_companies_name_normalized` y `ux_users_email` y capturan `23505`), el cargador (`CreateScope`) y la siembra (`CreateScope` + `FindByEmailAsync`). `me` no consulta la base de datos (DD-6).

**Prueba de arquitectura de la lista cerrada:** analiza el código fuente de `src/` (el mismo enfoque que `Src_DoesNotHardcodeModelNames`) y exige que `IgnoreQueryFilters` aparezca solo en esos dos archivos y con el recuento exacto, cada uno con el comentario `// company-filter-bypass: <motivo>`. Añadir un tercer uso exige tocar la prueba y revisar la decisión.

**APIs que evitan el filtro, prohibidas en `src/` fuera de `Migrations/`:** `.Find(`, `.FindAsync(` (no aplican el filtro), `FromSql`, `FromSqlRaw`, `FromSqlInterpolated`, `ExecuteSql*`, `SqlQuery*`, `ExecuteUpdate`, `ExecuteDelete`, `Database.GetDbConnection` y el uso de `Npgsql` en código de consulta (el `catch` de `PostgresException` en los almacenes sigue permitido). Las migraciones son SQL controlado y quedan exentas.

**Otras guardas de arquitectura:** (a) `openapi.json` no contiene un parámetro ni una propiedad llamados `companyId` (sin distinguir mayúsculas; `companyName` es válido); (b) ningún tipo de petición del Api ni comando de Application declara `CompanyId` (barrido por reflexión); (c) el literal `"cid"` se usa solo en `JwtDefaults`, el emisor, el validador y `HttpContextCurrentUser`/el middleware (y `"cname"`, solo en `JwtDefaults`, el emisor y el lector de `me` y de la Web); (d) los repositorios y almacenes no reciben `Guid companyId` como parámetro de consulta (salvo `CompanyRepository.FindLoginInfoAsync`, el registro de ejecución y el protector); (e) `AssistantAuditAppendOnlyTests` sigue vigente; (f) lista cerrada de llamadores de `ICompanyScopeFactory.CreateScope` en `src/` (DD-7; cada llamador nuevo exige tocar la prueba) y marcador `SkipCompanyContext` solo en `register-company`.

### DD-10. Filtros de consulta con nombre de EF Core 10: spike, sin depender de ellos

EF Core 10 documenta filtros con nombre (varios filtros por entidad con `IgnoreQueryFilters` selectivo); que 10.0.12 los ofrezca **no está verificado** (V-2). Decisión: este cambio usa **un único filtro sin nombre** y el diseño funciona igual con o sin esa característica. El spike (primera tarea de la PR 3, con prueba en rojo) comprueba la API contra la versión fijada; si existe, se registra y se valora adoptarla en un cambio posterior (por ejemplo, para combinar con borrado lógico) sin cambiar el contrato. No se sube de versión de paquetes por este motivo.

### DD-11. 404 idéntico y comportamiento de los repositorios

`FindDirectReportAsync(managerId, memberId)`, `ListDirectReportsAsync`, `FindDisplayNameAsync`, `TimeEntryRepository` y `DemoTimeEntryStore` no cambian de firma: el filtro los acota a la compañía. Un identificador de otra compañía es, para la consulta, un identificador inexistente, de modo que el caso de uso devuelve el mismo `null` y el endpoint el mismo 404 con el mismo cuerpo (`application/problem+json`, `title` «Recurso no encontrado», sin `detail`; idéntico salvo `traceId`; prueba que compara código, cabeceras relevantes y cuerpo). La ventana de fechas se valida antes que el miembro (un `from` futuro da el mismo 400 con un miembro ajeno que con uno propio). `ICurrentUser.CompanyId` se pasa solo donde se **crea** una fila (`TimeEntry.Start...`, `UserAccount.Create`), y la guarda lo comprueba. Las herramientas del asistente (`AssistantToolset`) heredan el aislamiento: un GUID de B inyectado en el mensaje se resuelve contra el contexto de A y da el mismo resultado que un GUID inexistente.

### DD-12. RLS de PostgreSQL: diferida

El rol de la aplicación es propietario de las tablas (ADR 0019): un propietario no está sometido a RLS salvo `FORCE ROW LEVEL SECURITY`, y además puede deshabilitar triggers y políticas. No se aborda ahora porque exige un rediseño de roles y del pool. **Camino futuro (se documenta en el ADR 0020):** (1) dos roles: `tt_migrator` (propietario, solo migraciones) y `tt_app` (sin `BYPASSRLS`, sin propiedad); (2) `ALTER TABLE ... ENABLE` y `FORCE ROW LEVEL SECURITY` con políticas `USING (company_id = current_setting('app.company_id', true)::uuid)`; (3) un `DbConnectionInterceptor` de Npgsql que ejecute `set_config('app.company_id', ..., false)` al abrir la conexión y la reponga (`RESET`/`DISCARD`) al devolverla al pool, porque el pool reutiliza sesiones; (4) las rutas de la lista cerrada (login, poller, versiones) pasan a funciones `SECURITY DEFINER` o a un rol con `BYPASSRLS` acotado; (5) cadena de conexión de migración distinta de la de la aplicación (hoy es una sola). Mientras tanto, la protección de la tercera capa es el esquema y las pruebas.

### DD-13. Asistente por compañía: almacén, resolución y compañía de plataforma

- `AssistantSettingsStore` (con ámbito) no cambia de firma: `GetAsync`, `GetVersionAsync`, `SaveAsync` y `DeleteAsync` leen/escriben la fila de **su** compañía por el filtro; `SaveAsync` fija `row.CompanyId = ICompanyContext.CompanyId` al insertar y la guarda lo verifica. «Sin fila» sigue siendo token `"0"`; un `INSERT` concurrente de la misma compañía viola la PK (`23505`) y da `Conflict`, como hoy. La auditoría se inserta con la misma compañía en la misma transacción. `xmin` se conserva.
- `AssistantSettingsResolver.Resolve(env, stored, storedCredentialUsable)` gana el argumento `platformDefaults` (= `Company.UsesPlatformAssistant`). Sin fila: plataforma (la compañía demo) -> el entorno de hoy; no plataforma -> **`provider` = `None` (origen `default`), `model` nulo (origen `default`), `credentialConfigured = false` (origen `none`)**, y `timeoutSeconds` y `maxOutputTokens` con los valores por defecto de plataforma (origen `env`) (asistente deshabilitado; spec `assistant-settings`). Con fila: gana la fila; la clave de entorno `Ai__ApiKey` solo se usa si `platformDefaults` y el proveedor efectivo es el del entorno; el tiempo máximo y los tokens siguen heredando del entorno cuando la fila es nula (son valores no secretos de plataforma); **el modelo y el esfuerzo del entorno solo valen para la compañía de plataforma** (la spec `assistant-settings` fija que `provider`, `model` y la clave de una compañía que no es la demo provienen únicamente de su fila; aplicado en la PR 4a, ver «Desviaciones de la PR 4a»). El resultado de «sin fila» y el de «`None` guardado» son indistinguibles para el chat (503 genérico).
- `Ai__AllowedProviders` sigue siendo una lista de **plataforma**: las compañías nuevas eligen entre ella, con su propia clave. Un proveedor `Ollama` en la lista da a todas las compañías acceso al `Ai__Endpoint` del operador; es una decisión explícita del operador al incluirlo (riesgo anotado).
- La prueba de conexión usa solo la configuración efectiva de la compañía propia: un candidato sin clave nueva usa la clave guardada de **esa** compañía o la de plataforma solo si `platformDefaults`; nunca la de otra. Los límites de tasa por persona (3 por minuto, `sub`) no cambian.
- `GET`/`PUT`/`DELETE` quedan acotados por el filtro: no existe un identificador de compañía en el contrato. Cualquier Manager de la compañía edita la configuración (**riesgo aceptado**, ahora acotado a la compañía; se documenta en el ADR 0021 y en el aviso de la página).

### DD-14. Runtime: registro de instantáneas por compañía

El singleton `AssistantChatClient` + `AssistantSettingsLoader` se sustituye por `AssistantRuntimeRegistry` (singleton, Infrastructure):

```
ChatAssistantEngine ──GetAsync(companyId)──> Registry ──hit──> CompanyRuntime(holder AssistantChatClient, LastUsed)
                                                 │ miss: carga única por compañía (Lazy<Task>)
                                                 └─> ICompanyScopeFactory.CreateScope(companyId) ─> store.GetAsync ─> resolver ─> fábrica ─> Swap
Poller ──ListVersionsAsync()──> para cada CompanyRuntime cargada: si versión distinta -> ReloadAsync(companyId)
```

| Aspecto | Diseño |
|---|---|
| Construcción perezosa | La primera pregunta de una compañía crea su `CompanyRuntime` con una carga protegida por un `Lazy<Task>` por compañía (una sola carga concurrente). Una compañía sin fila y sin plataforma obtiene la instantánea `Disabled` (sin pipeline ni `HttpClient`) |
| Sustitución por `xmin` | Igual que hoy por compañía: `Swap(inner, options, version)`, publicación con `Interlocked.Exchange`, **gracia de 120 s** para liberar la instantánea anterior (toda petición dura <= 55 s) |
| Conservar la última válida | Si la fila de una compañía es inválida, no descifrable o con proveedor no permitido, no hay `Swap` y se registra un aviso **una vez por versión rechazada y compañía** (`LastRejectedVersion` por compañía), sin secretos. **Primera fila inválida** (sin instantánea válida previa): la compañía queda con la instantánea `Disabled` (asistente deshabilitado para esa compañía, `503`); nunca se recurre a la configuración o la clave de plataforma, tampoco para la compañía demo |
| Fallos transitorios | El `Lazy<Task>` de carga **no cachea una tarea fallida** (base de datos caída, tiempo agotado): si la carga lanza una excepción de infraestructura se retira la entrada del diccionario, la petición que la sufre recibe el `503` genérico de «asistente no disponible» y la **siguiente petición de esa compañía reintenta** la carga. Solo se cachean resultados determinados (instantánea válida o `Disabled` por falta de fila o por fila inválida) |
| Memoria | Un pipeline y un `HttpClient` propios (`OwnedHttpClientChatClient`) por compañía **con proveedor activo**. Tope `Ai__MaxLoadedCompanies` (valor por defecto **100**, rango 1 a 1000, fijado por la spec `assistant-configuration` y confirmado por el usuario; se mide en V-8). Las `Disabled` apenas pesan y no cuentan para el tope |
| Expulsión | Al superar el tope se expulsa la compañía menos usada recientemente (LRU por `LastUsed` con `TimeProvider`): `Swap(Disabled)` + retirada del diccionario; el pipeline anterior se libera tras la gracia de 120 s, por lo que una petición en curso termina bien. Además, caducidad por inactividad (`Ai__RuntimeIdleMinutes`, propuesta 60) para todas las entradas. La compañía expulsada se recarga sola en su siguiente pregunta |
| Sobrecarga | Si más compañías activas que el tope compiten, hay expulsiones y recargas repetidas (latencia de una lectura y de una construcción de cliente). Se registra un aviso con límite de frecuencia; el operador sube el tope. No se rechazan preguntas por capacidad |
| Escritura local | Tras el `Save`/`Delete`, el caso de uso llama a `IAssistantRuntimeReloader.ReloadAsync(companyId, ct)`; si la compañía no está cargada, no hace nada (carga perezosa). Si la recarga falla, el guardado ya está confirmado: 200 y aviso, como hoy |
| Motor | `ChatAssistantEngine` obtiene la instantánea una vez por petición con `registry.GetAsync(currentUser.CompanyId)` y deja de usar el singleton |

Compañía de plataforma: la carga resuelve el entorno completo; la clave de plataforma nunca llega a una compañía que no sea de plataforma.

**Puente transitorio (PR 1b a 4b).** El runtime singleton y el poller actuales leen `assistant_settings` fuera del HTTP (singleton, sin petición). Para que las PR 1b, 2 y 3 sean desplegables sin cambiar el comportamiento, **el puente entra en la PR 1b**: en esa PR, `AssistantSettingsRecord` y `AssistantSettingsStore` pasan a la clave primaria `company_id` usando siempre `Company.DefaultId` (el contexto fijo de la PR 1), y el cargador y el poller leen la fila de esa compañía, de modo que la configuración guardada sigue llegando al runtime y la clave `Ai__ApiKey` del entorno se usa solo como antes (la compañía por defecto tiene `uses_platform_assistant = true`). En la PR 2, al sustituir el contexto fijo por el ambiental (vacío fuera de HTTP), el puente pasa a leer con `CreateScope(Company.DefaultId)`; la PR 3 comprueba que sigue viendo su fila con el filtro activo. La PR 4a generaliza el almacén (la compañía sale del contexto, no de la constante) y la PR 4b retira el puente. **Mientras exista el puente, solo la compañía con `uses_platform_assistant` obtiene instantánea; cualquier otra compañía recibe el `503` de asistente deshabilitado: el puente nunca sirve a una compañía registrada con la clave de plataforma.** **Rollback de 4b:** antes de abrir el registro se puede revertir (vuelve el puente). Tras abrir el registro no hay `Down` ni se revierte 4b (las compañías registradas perderían su asistente propio): el plan es la corrección hacia delante descrita en DD-4.

**Aplicado en la PR 4a:** el motor singleton solo sirve a `Company.DefaultId` (guarda `ServesCompany`, sin consultar la base de datos) y el cargador lee el indicador `uses_platform_assistant` de la compañía por defecto antes de resolver: sin él, y sin fila, publica la instantánea deshabilitada (versión `disabled`), y con fila no hereda del entorno ni modelo, ni esfuerzo, ni `Ai__ApiKey`. `IAssistantRuntimeReloader.ReloadAsync(companyId, ct)` recarga el puente solo para la compañía por defecto y no hace nada para las demás (no hay instantánea que recargar).

**Aplicado en la PR 4b:** el puente se retira. `AssistantSettingsLoader`, `IAssistantSettingsLoader`, la guarda `ServesCompany` del motor y el `AssistantChatClient` singleton desaparecen; `ChatAssistantEngine` pide `registry.GetAsync(currentUser.CompanyId)` una vez por petición, `IAssistantRuntimeReloader.ReloadAsync(companyId)` recarga la compañía indicada si está cargada y la lista cerrada de `CreateScope` declara el lector del registro (`CompanySettingsReader`) en lugar del cargador. Ver «Desviaciones y aclaraciones del diseño surgidas en la PR 4b».

### DD-15. Poller global

`AssistantSettingsPoller` se mantiene como un único `BackgroundService` (cada `Ai__SettingsPollSeconds`, 30 por defecto). Su vuelta: `store.ListVersionsAsync()` (sitio 2 de la lista cerrada, una sola consulta `SELECT company_id, xmin FROM assistant_settings` sin entidades con seguimiento) y, para cada `CompanyRuntime` **ya cargada**, compara su versión con la de la fila (`"0"` si no hay fila; una fila nueva para una entrada `"0"` cuenta como cambio) y recarga solo las distintas, con un máximo de recargas en paralelo y sin propagar errores (aviso una vez por racha, como hoy). Las compañías no cargadas se ignoran: cargarán la fila fresca en su primera pregunta. También aplica la expulsión por inactividad. La primera carga acotada en `StartAsync` (10 s) se conserva: precarga solo la compañía de plataforma (para que el primer chat de la demo use la fila ya guardada) y deja el resto en lazy. Consistencia eventual <= `SettingsPollSeconds`. Alternativa descartada: comprobar la versión de la compañía en cada pregunta (una consulta por pregunta, contra el principio de poller ya decidido).

### DD-17. Cifrado con AAD `company_id` (formato v2)

`AssociatedData` pasa a `tt-assistant-credential|v2|{companyId:D}|{provider}|{keyVersion}`. `Protect(plaintext, provider, companyId)` cifra siempre en v2. `TryUnprotect(stored, provider, companyId, out plaintext)` prueba **v2** y, si falla la autenticación, **v1 solo cuando `companyId == Company.DefaultId`**: los textos cifrados en v1 solo existen en la compañía por defecto, así que una fila v1 que aparezca en otra compañía (copia manual entre filas) no se descifra. No cambia el formato de almacenamiento (`credential_ciphertext`, `credential_nonce`, `credential_key_version`): la versión del AAD no se guarda, se deduce probando. `ReEncryptOrKeep` (ya existente en `SaveAssistantSettingsUseCase`) recifra en v2 en el primer guardado que conserve la clave (con o sin clave nueva); el cargador es de solo lectura y no migra el formato (leer no escribe: mismo `xmin`). Efecto: un texto cifrado de una compañía no se puede trasplantar a otra (mejora, no requisito de bloqueo; las claves maestras siguen siendo globales por entorno, DD-6 de `asistente-config-responsable`). **Naturaleza:** la spec `assistant-credential-protection` la define como mejora no bloqueante y recortable («DEBERÍA»); el aislamiento no depende de ella. **Límite documentado en el ADR 0020** (spec): un registro v1 no está vinculado a la compañía hasta recifrarse. Decisión (Q-15 resuelta; recogida en la spec `assistant-credential-protection`): no se guarda un identificador de formato; se deduce probando v2 y luego v1 solo para `Company.DefaultId` (más estricto, sin cambio de esquema).

### DD-20. Política de contraseñas

`PasswordPolicy` (Application, pura): mínimo **12**, máximo **128** (el tope existente de `LoginUseCase.MaxPasswordLength`), medido en caracteres, **sin reglas de composición**, y **sin recortar ni normalizar los espacios** (se verifica con los espacios exteriores). | `GET /api/auth/me` | Autenticado, permitido con `mcp` | — | `user` con `companyName` y `mustChangePassword` **tomados de los claims `cname` y `mcp`, sin consultar la base de datos** (DD-6) | 401 |

**Decisión del usuario, regenerar la contraseña temporal:** el usuario decidió **incluir** la regeneración, **solo antes del primer acceso** (`must_change_password = true`) y **solo por el responsable directo** de la persona (mínimo privilegio, AGENTS §6: no por cualquier Manager de la compañía). La spec `employee-management` ya contiene el requisito «Regenerar la contraseña temporal» (con su operación y la regla «`temporaryPassword` solo en las respuestas del alta y de regenerar» en el requisito de contrato OpenAPI) y la spec `web-session` la acción de la página de equipo; la tarea V-13 solo comprueba esa coherencia.

- **Quién y dónde:** `CompanyId` sale de `ICurrentUser`. `managerId` **por defecto es el Manager que crea, también cuando el nuevo usuario es Manager** (spec); si se indica otro, debe existir **en la misma compañía** (el filtro lo oculta si es ajeno -> 400 con error en `managerId`, idéntico para inexistente y ajeno) y tener rol `Manager`; además la FK compuesta lo garantiza (`23503` se traduce al mismo 400, defensa en profundidad). No se crean jerarquías nuevas: el equipo sigue siendo el de reportes directos (si `m1` crea a `m2` y `m2` crea a `e`, el equipo de `m1` contiene a `m2` y no a `e`). La spec solo exige que el responsable indicado sea un usuario de la misma compañía; exigir además rol `Manager` es regla de diseño, alineada con tasks 6.4 (Q-4 resuelta por la spec en lo del valor por defecto).
- **Contraseña temporal:** la genera el servidor (`ITemporaryPasswordGenerator`, 16 caracteres de un alfabeto sin ambigüedades con `RandomNumberGenerator`, unas 80 bits; cumple la política por construcción), se devuelve **una sola vez** en la respuesta `201` del alta (y en la de regenerar) y no se guarda en claro, ni se escribe en registros, ni aparece en filas de auditoría ni en ninguna otra respuesta; en el contrato, `temporaryPassword` figura solo en los esquemas de respuesta del alta y de regenerar (V-12 comprueba que ninguna prueba del contrato la prohíbe por nombre). Tras el cambio, la temporal deja de ser válida (login con ella: 401 genérico). Que la genere el servidor evita que un Manager fije contraseñas débiles o reutilizadas.
- **Regenerar** solo mientras `must_change_password = true` (nunca ha entrado) y solo por el **responsable directo** (`FindDirectReportAsync(managerId, memberId)`; para cualquier otro, sea Manager de la misma compañía o de otra, el mismo `404` que un identificador inexistente): sin ella, una persona que pierde la contraseña temporal quedaría bloqueada, porque el correo ya existe (409) y no hay recuperación por correo. Usa la operación de dominio `RegenerateTemporaryPassword(hash)` (sustituye el hash y mantiene la marca); la anterior deja de iniciar sesión.
- **Concurrencia (`xmin`):** `ChangePassword` y la regeneración guardan con el token de concurrencia `xmin` de la fila de `users` (DD-2). Carrera típica: la persona cambia su contraseña entre la lectura y el guardado del Manager; el guardado del Manager falla (`DbUpdateConcurrencyException` → `409`) y no pisa la contraseña elegida por la persona (y a la inversa: si el Manager regenera entre la lectura y el guardado de la persona, el cambio de la persona recibe `409`). Los casos de uso no reintentan: el cliente repite la operación.
- **Caducidad y token `mcp` (riesgo aceptado):** la contraseña temporal **no caduca por tiempo** (no hay caducidad en este cambio); el runbook (PR 8) incluye revisar periódicamente las cuentas con `must_change_password` antigua. Un token `mcp` ya emitido **no se invalida** al regenerar la contraseña temporal (caduca como máximo a los 30 minutos; no hay revocación). Ambos puntos se anotan en el ADR 0022.
- **Cambio forzado de verdad:** el token de una persona con `must_change_password` lleva `mcp=true`. `PasswordChangePendingMiddleware` (tras la autenticación) decide **solo por el claim** (sin consultar la base de datos) y responde **403** `application/problem+json` con `title` «Acceso denegado» (el `detail` puede explicar que debe cambiar su contraseña antes de continuar) a todo endpoint que no lleve el marcador de metadatos `AllowWhilePasswordChangePending` (solo `change-password` y `me`); incluye el asistente. Un token sin `mcp` o con `mcp` distinto de `true` se trata como sin cambio pendiente. Se hace con middleware y no con una política porque las políticas por rol (`Manager`) no lo heredarían. Tras el cambio se emite un token nuevo sin `mcp`; el antiguo sigue bloqueado hasta caducar (como máximo 30 minutos). `ChangePassword` comprueba antes que la compañía del usuario está `Active` (si no, el mismo `401` genérico del login, sin emitir token ni cambiar nada; DD-6), verifica la actual con el hasher (tiempo constante en la verificación), exige que la nueva cumpla `PasswordPolicy` y sea distinta de la actual y pone `MustChangePassword=false` guardando con el token `xmin`.
- **Tope de empleados (exacto bajo concurrencia):** `Company__MaxEmployees` (50 por defecto, rango 1 a 1000; no editable por el Manager; sin operación del contrato que lo cambie). La spec exige que con el tope a una persona de ser alcanzado y 5 altas simultáneas haya **exactamente un `201`** y cuatro `409`; la versión anterior del diseño aceptaba un «tope blando» y queda **descartada**. Mecanismo por defecto: el recuento (con el filtro) y la inserción se hacen en una **transacción `Serializable` con reintento acotado ante `40001`** (serialization_failure; válida entre instancias, sin SQL crudo; el recuento vive en `IUserRepository`). Alternativa de reserva si V-14 la prefiere: cerrojo en memoria por compañía (`SemaphoreSlim` por clave; válido con una instancia, coherente con ADR 0017). Se decide y se anota en V-14 (tarea 6.3) y en el ADR 0022. El tope de una compañía no afecta a otra.
- **Rol y alta:** un Manager puede crear otros Managers **solo en su compañía** (la guarda y la FK lo imponen); el nuevo Manager no accede a datos ni a la configuración del asistente de otra compañía, y sí puede editar la de la suya (riesgo aceptado). No hay baja de usuarios ni cambio de rol en este cambio.
- El correo pasa por `UserAccount.NormalizeEmail` y el alta falla por `ux_users_email` (`23505`) -> 409 con `detail` genérico, sin pre-consulta (sin carrera).

### DD-22. Siembra y compañía demo idempotente

`DemoUsersSeeder` y `DemoDataSeeder` trabajan dentro de `ICompanyScopeFactory.CreateScope(Company.DefaultId)`. La compañía por defecto la crea la migración A; el sembrador la «crea o encuentra» de forma idempotente (si faltara, la inserta con el id fijo y trata `23505` como existente). Para cada usuario de demostración usa `FindByEmailAsync` (sitio 1 de la lista): si existe en la compañía demo, **no lo modifica ni lo duplica** y los vínculos apuntan al id vigente de Marta; si existe en **otra compañía**, **el arranque falla** con un mensaje claro sin la contraseña y sin modificar ninguna compañía (spec `team-access`; las tareas 1.11 y 3.11 lo prueban). Los usuarios demo se siembran con `must_change_password = false`. Los fichajes de demostración llevan `CompanyId` de la demo. **Apagado de la siembra pública al abrir el registro:** `RegistrationOptionsValidator` hace fallar el arranque (mensaje con ambas claves, sin valores) si `Registration:Enabled=true` y `Seed:DemoUsers=true`. Los usuarios de demostración que ya existan en producción (contraseña pública) **siguen existiendo** al apagar la siembra. Orden de la apertura del registro (runbook y tarea 9): 1) `Seed__DemoUsers=false`; 2) comprobar que no se recrean; 3) retirar los usuarios demo (copia previa y script revisado, borrando antes sus fichajes por la FK) o reiniciar la base de datos si solo contiene datos de demostración (V-1; **Q-1 sigue siendo una decisión previa del responsable**: qué hacer con la compañía Demo si tiene usuarios reales); 4) definir `Registration__InviteCodes`; 5) `Registration__Enabled=true`. Como red de seguridad, un **validador de arranque en `Production`** hace fallar el arranque con un mensaje claro si `Registration:Enabled` es `true` y existe algún usuario con correo del dominio demo (`@example.test`) en la compañía por defecto (spec `startup-configuration`): se ejecuta tras las migraciones y antes de atender peticiones, mediante `CreateScope(Company.DefaultId)` y una consulta `ExistsWithEmailDomainAsync` del repositorio de usuarios (sin `IgnoreQueryFilters`: basta el ámbito de la compañía por defecto porque los usuarios demo con contraseña pública solo se siembran en ella; no se detecta un correo `@example.test` de otra compañía, que no tendría esa contraseña). La demo conserva la clave de plataforma, acotada por `Ai__DailyRequestsPerCompany`. La validación de la exclusión ocurre antes de cualquier migración o siembra y el mensaje no imprime ni la contraseña demo ni ningún código.

**Desviaciones y aclaraciones del diseño surgidas en la PR 1:**

1. **La PK de `assistant_settings` no cambia en la PR 1.** La sección 4 pedía el modelo final también para `assistant_settings`, pero cambiar su clave primaria a `company_id` en el modelo rompería el almacén (que sigue leyendo y escribiendo con `id = 1`) contra el esquema A, y `has-pending-model-changes` no quedaría vacío si el modelo y el snapshot difirieran. En la PR 1 el modelo de `assistant_settings` conserva la PK `id` y gana `company_id` (obligatorio en el modelo, anulable en la base hasta la B; el registro lo rellena con `Company.DefaultId`); el cambio de PK, `AssistantSettingsRecord` y el almacén van juntos en la 1b, como ya decía la tarea 1b.8b.
2. **Índices de apoyo creados por convención de EF.** Las claves foráneas añadidas al modelo generan dos índices que el diseño no listaba: `ix_time_entries_company_id_employee_id` (apoyo de la clave compuesta del empleado, que también cubre la FK a `companies`) e `ix_assistant_settings_company_id` (apoyo de la FK a `companies`). No se pudo suprimir la convención. La migración A **no** los crea (A no añade índices, claves únicas ni claves foráneas nuevas); **la B debe crearlos** junto con el resto, y `ix_assistant_settings_company_id` desaparece en la 1b cuando `company_id` pasa a ser la clave primaria.
3. **Contexto de compañía de la PR 1.** `ICompanyContext` (puerto en `Application/Identity`) tiene una implementación fija transitoria, `FixedCompanyContext` (Infrastructure), registrada con ámbito `Scoped`; `TimeTrackerDbContext` **no** lo recibe todavía (no hay filtro hasta la PR 3; recibirlo sin usarlo es un parámetro sin leer que el compilador rechaza con `-warnaserror`). `DesignTimeDbContextFactory` no cambia por lo mismo. `ClockInUseCase` y las siembras toman la compañía del contexto fijo; la PR 2 lo sustituye por `ICurrentUser.CompanyId` y el contexto ambiental.

2. **`IAssistantEngine`.** `IsEnabled` pasa a `GetAvailabilityAsync` (`Enabled`, `Disabled`, `Unavailable`): un fallo de infraestructura al cargar la compañía no se cachea ni se oculta como «deshabilitado», la petición recibe el `503` genérico de «no disponible» (distinto detalle que el de deshabilitado) y la siguiente reintenta. El motor es de ámbito de petición y guarda la instantánea que lee la primera vez (una sola lectura por petición).
3. **Sondeo con una consulta que incluye el indicador.** `ListVersionsAsync` hace un `LEFT JOIN` de `companies` con `assistant_settings` (con `IgnoreQueryFilters` solo sobre la segunda) y devuelve una entrada por compañía con su versión (`"0"` sin fila) y `uses_platform_assistant`: es una consulta, sin entidades con seguimiento, y permite recargar cuando cambia el indicador aunque no cambie la fila (aviso de la revisión de la PR 4a). Una compañía que pierde el indicador pasa a deshabilitada en la siguiente recarga; si además su fila queda rechazada, **no se conserva la última válida** (pudo construirse con la clave de plataforma): se degrada a deshabilitado. Limitación: si el indicador cambia de falso a verdadero y la fila de esa compañía queda rechazada, el sondeo vuelve a leerla en cada vuelta (sin repetir el aviso).
4. **Precarga y sondeo como servicio interno.** `AssistantSettingsPoller` pasa a `internal`; Api lo registra con `AddAssistantSettingsPoller()`. La precarga acotada de 10 s carga solo la compañía por defecto; un fallo no impide arrancar.
5. **El tope de compañías cargadas cuenta solo las que tienen proveedor activo** (las deshabilitadas apenas pesan), como decía DD-14; la expulsión es por menos usada (`LastUsed`) y caduca además por inactividad en cada vuelta del sondeo; el aviso de sobrecarga se repite como mucho cada 5 minutos.
6. **Valor no numérico de los topes.** El enlazador de configuración de .NET repite el valor en su excepción; `AiOptionsBinder` comprueba antes las cuatro claves nuevas y falla con `Ai:{clave}: debe ser un número entero.` sin imprimir el valor.
7. **Minuto de compañía y `400` por cuerpo ausente.** El `400` de «cuerpo ausente o ilegible» que se produce antes de llamar al caso de uso (o al enlazar el cuerpo) no cuenta para el minuto de la compañía; sí cuentan los `400` de validación y los `503`.
8. **Guardar con la compañía no cargada.** `ReloadAsync(companyId)` no hace nada si la compañía no está cargada: la primera pregunta construye su instantánea con la fila ya guardada (lo comprueban `Put_Valid...` y `AssistantRuntimeIsolationTests`).
9. **Pruebas.** Las fábricas de pruebas sin base de datos (`AssistantApiFactory`) sustituyen el registro por uno fijo (`FixedRuntimeRegistry`, un cliente falso por compañía). Se retiran `AssistantSettingsLoaderTests` y `FakeSettingsLoader` (sus escenarios pasan a `AssistantRuntimeRegistryTests`, `CompanySettingsReaderTests` y `AssistantSettingsPollerTests`) y las dos pruebas del puente de `AssistantEndpointDisabledTests` que ya no tienen sentido.

**Desviaciones y aclaraciones del diseño surgidas en la PR 5:**

1. **El ejemplo de la spec `corto-secreto-prueba` no es «demasiado corto».** La spec `startup-configuration` lo cita como código de menos de 16 caracteres, pero mide 20 y por tanto es válido. La prueba de «el valor no se imprime» usa `corto-secreto-1` (15 caracteres), que sí falla, y comprueba que ninguna excepción lo contiene.
2. **`Hops < 1` ya lo detenía `AddForwardedHeadersBehindProxy`.** Con `ForwardedHeaders:Enabled=true` y `Hops` menor que 1 el arranque falla al registrar el tratamiento de las cabeceras (antes de cualquier migración o siembra), nombrando `ForwardedHeaders:Hops`. El validador del registro solo añade la exigencia de que `ForwardedHeaders:Enabled` sea `true` en `Production`; la escena «saltos no válidos» de la spec se cumple por ese camino (la prueba nació «verde a la primera»; el mensaje existente se amplía con la razón que pide la spec: el límite por IP).
3. **Las opciones se validan al leerlas, no en `ValidateOnStart`.** `MapRegistrationEndpoint` lee `IOptions<RegistrationOptions>` al componer la aplicación (antes de que arranque ningún servicio alojado), así que un conflicto con la siembra o con `ForwardedHeaders` falla **antes de la migración y de la siembra** (lo comprueban las pruebas contra una base vacía con `Database__ApplyMigrationsOnStartup=true`, que debe seguir sin tablas). `ValidateOnStart` se mantiene como red.
4. **`RegisterCompanyResult.Created` lleva `CompanyId`.** Solo para el registro de metadatos (el resultado y el identificador de la compañía creada); el cuerpo de la respuesta sigue sin ningún identificador de compañía.
5. **Predicados de dominio.** `Company.IsValidName`, `UserAccount.IsValidEmail` y `UserAccount.IsValidDisplayName` (con pruebas de dominio) comparten la regla con `Create`: el caso de uso valida por campo sin duplicar los límites ni capturar excepciones.
6. **Un cuerpo sin tipo de contenido JSON no llega al endpoint.** Una petición anónima con un `Content-Type` que no es JSON (por ejemplo `text/plain`) no casa con el endpoint (metadatos de `Accepts` inferidos del cuerpo) y recibe el `401` de la política de respaldo, igual que ocurre ya con el login. Un cuerpo realmente ausente o un JSON roto dan `400`. No cambia la seguridad; se anota por si el cliente espera un `415`.
7. **`dotnet build src/TimeTracker.Api --no-incremental` y el SHA-256.** Se comprobó a mano (no como prueba, para no lanzar una compilación dentro de otra): el `docs/api/openapi.json` regenerado con `--no-incremental` tiene el mismo SHA-256 que el versionado. Esta PR añade solo `/api/auth/register-company` (y el esquema `RegisterCompanyRequest`); la prueba `ExportedDocument_DoesNotYetContainTheOperationsOfThePasswordAndEmployeesEntrega` lo vigila y la PR 6 (tarea 6.14) la sustituye.
8. **Lista cerrada de `CreateScope`.** Declara `CompanyRegistrationStore` (tarea 5.5) y `DemoUsersStartupGuard` (tarea 5.11b).
9. **`EnvironmentIsolation` de las pruebas** borra también `Registration__`, `Company__` y `ForwardedHeaders__` del entorno del proceso de pruebas, junto con los prefijos anteriores.
10. **Registro de rechazos por límite.** El `429` de `register-company` registra su resultado (`RejectedByRateLimit`) con el mismo formato de solo metadatos que el resto de intentos; el manejador de rechazos del limitador lo emite al ver la política.
