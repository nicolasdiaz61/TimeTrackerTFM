## Convenciones de ejecución

- **Strict TDD**: cada tarea de código = RED (prueba que falla; se anota el mensaje real y **qué prueba** es) → GREEN (código mínimo) → REFACTOR (suite en verde). Si una prueba pasa a la primera, se marca «verde a la primera» con justificación y mutación temporal.
- Las pruebas **nunca llaman a un proveedor real de IA**: solo `FakeChatClient` y dobles. Valores inventados y reconocibles: `clave-prueba-123456`, `codigo-prueba-0123456789`, `contrasena-prueba-12345`, `ana@example.test`. Ningún secreto, código de invitación ni clave real en disco, `.env`, registros ni comandos.
- Pruebas de aislamiento: fábrica `TwoCompanyFixture` (compañías A y B, cada una con un Manager y dos Employees), reutilizada por todas las pruebas A/B.
- Identificadores de código en inglés; documentación y textos de usuario en español neutro.
- Entorno limpio antes de probar: `Get-ChildItem Env: | Where-Object Name -Match '^(Cors__|ConnectionStrings__|Database__|Jwt__|Seed__|Ai__|Registration__|Company__|ForwardedHeaders__|ASPNETCORE_|DOTNET_ENVIRONMENT)'` sin resultados. Docker en marcha para integración (PostgreSQL 18, Testcontainers); **no se tocan contenedores existentes** (solo `docker info` y `docker ps` de lectura; Testcontainers crea y retira los suyos).
- **Copia previa** de los archivos a modificar en `..\TimeTracker.rollback\pr-N\` antes de cada PR.
- **Verificaciones (`V-n`)**: cada una se ejecuta **antes** de la tarea que depende de ella; el resultado se anota en `design.md` (sección «Resultados de V-n en apply») y, si falla, se detiene la tarea dependiente y se consulta al usuario. Las verificaciones sobre producción (Railway) las ejecuta o autoriza el responsable: apply no accede a producción por su cuenta.
- Rutas: `APP` = `src/TimeTracker.Application` · `DOM` = `src/TimeTracker.Domain` · `INF` = `src/TimeTracker.Infrastructure` · `API` = `src/TimeTracker.Api` · `WEB` = `src/TimeTracker.Web` · `DT` = `tests/TimeTracker.Domain.Tests` · `AT` = `tests/TimeTracker.Application.Tests` · `IFT` = `tests/TimeTracker.Infrastructure.Tests` · `IT` = `tests/TimeTracker.Api.IntegrationTests` · `AR` = `tests/TimeTracker.ArchitectureTests` · `WT` = `tests/TimeTracker.Web.Tests`. (Si algún proyecto de pruebas tiene otro nombre, se ajusta en la copia previa de cada PR.)

| Alias | Comando |
|---|---|
| `RESTORE` / `BUILD` | `dotnet restore TimeTracker.sln` / `dotnet build TimeTracker.sln -c Release --no-restore -warnaserror` |
| `TEST` | `dotnet test TimeTracker.sln -c Release --no-build --collect:"XPlat Code Coverage" --results-directory TestResults` |
| `COV-A` / `COV-D` | `pwsh scripts/check-coverage.ps1 -ResultsDirectory TestResults -Package TimeTracker.Application -MinimumPercent 80` / `... TimeTracker.Domain -MinimumPercent 100` |
| `FORMAT` | `dotnet format TimeTracker.sln --verify-no-changes --no-restore` |
| `VULN` | `$env:DOTNET_CLI_UI_LANGUAGE='en'; dotnet list TimeTracker.sln package --vulnerable --include-transitive` (sin `has the following vulnerable packages`) |
| `EF-PENDING` | `dotnet ef migrations has-pending-model-changes --project src/TimeTracker.Infrastructure --startup-project src/TimeTracker.Api` (sin cambios pendientes) |
| `DOCKER-CHECK` | `docker info` (solo lectura; confirma que el motor responde sin listar ni detener contenedores) |
| `T-x` | `dotnet test tests/<proyecto> --filter "FullyQualifiedName~Clase"` |

**Puerta de cada PR**: `DOCKER-CHECK` → `RESTORE` → `BUILD` → `TEST` (todas las suites: dominio, aplicación, infraestructura, integración, arquitectura, Web) → `COV-A` → `COV-D` → `FORMAT` → `VULN`, todo en verde (y `EF-PENDING` en las PR con modelo o migración), y PARADA para revisión con contexto limpio. Cada PR indica además su **tamaño estimado**, sus **riesgos** y **qué se puede desplegar tras ella**. `DocumentGeneration` exporta el contrato al compilar `API`: el host debe arrancar con el entorno limpio.
